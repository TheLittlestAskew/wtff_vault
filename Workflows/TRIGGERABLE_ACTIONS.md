# Workflows — Triggerable Actions Index

Every action you can trigger from the `Workflows/` folder and its subfolders: what it
does, and how to fire it. Generated by auditing each file.

**Path shorthand:** `~` = `C:\Users\theli\Obsidian Vaults\wtff_vault` (the vault root). Most Node scripts
hard-code the vault root, but several read files relative to their own folder, so the
**"Run from"** column matters — run them from the listed directory.

| Action | Type | How to trigger |
| --- | --- | --- |

| Approve a pending session (apply + push) | manual | double-click `Approve-WTFF.cmd`, the toast "Approve & apply" button, or `node wtff_pipeline_watch.js --approve` |

## 1. Session pipeline (the core automation)

The spine: a new recording is transcribed, spell-checked, paused for your review, then
(on approval) applied to a note, propagated across the vault, and pushed to git.

### `scripts\wtff_pipeline_watch.js` — watch mode
- **What:** Watches `~\Session_Sources\Recordings\`. When a new `.mp3` finishes copying, it
  refreshes keyterms, **refreshes party sheets** (see §4), transcribes the audio, runs
  Convo 1 Phase A (spell-check only), then **stops and pings you** for review. Applies nothing yet.
- **Trigger (automatic):** drop/record an `.mp3` into the Recordings folder.
- **Trigger (manual):** `node wtff_pipeline_watch.js` (from `~\Workflows\scripts`). Leave it running.
- **Run from:** `~\Workflows\scripts`

### `scripts\wtff_pipeline_watch.js --approve` — approve mode
- **What:** After you've reviewed the spell-check file, this runs Convo 1 Phase B (apply
  corrections + generate the session note) then Convo 2 (propagate across the vault + git
  commit/push). Reads the pending session from `~\_pipeline\state.json`.
- **Trigger:** any of —
  - double-click **`scripts\Approve-WTFF.cmd`**
  - the **"Approve & apply"** button on the review toast (from `wtff_notify.ps1`)
  - the **"Approve & apply"** button in the status window (`wtff_status_window.ps1`)
  - `node wtff_pipeline_watch.js --approve`
- **Run from:** `~\Workflows\scripts`

### `scripts\Approve-WTFF.cmd`
- **What:** Convenience wrapper that calls `wtff_pipeline_watch.js --approve` in a titled window.
- **Trigger:** double-click, or it's launched by the toast / status-window approve buttons.

### `scripts\run-watcher.cmd`
- **What:** Launches the watcher and tees all output to `~\_pipeline\watcher.log`.
- **Trigger:** double-click, or invoked by `start-watcher-hidden.vbs`.

### `scripts\start-watcher-hidden.vbs`
- **What:** Starts `run-watcher.cmd` with no visible window (stays running so the scheduled
  task shows "Running" and can auto-restart the watcher if it dies).
- **Trigger:** the **"WTFF Pipeline Watcher"** scheduled task at logon (see §7), or double-click.

## 2. Status window & notifications

### `scripts\Show-WTFF-Status.cmd` → `scripts\wtff_status_window.ps1`
- **What:** Opens a small WPF panel showing pipeline progress (Transcription → Spell-check →
  your review → Apply/notes → Propagate+push). Driven entirely off `~\_pipeline\status.json`
  + a tail of `watcher.log`, polled ~0.75s. Single-instance; safe to open/close anytime.
- **Triggerable actions *inside* the window** (visible only during the review gate):
  - **"Open spell-check"** → opens the proposed-corrections file for editing.
  - **"Approve & apply"** → launches `Approve-WTFF.cmd` (the approve step above).
- **Trigger the window:** double-click `Show-WTFF-Status.cmd`; the watcher also opens it
  automatically when a run starts.
- **Self-test:** set env `WTFF_STATUS_SELFTEST=1` to auto-close after ~2.5s (for smoke runs).

### `scripts\wtff_notify.ps1`
- **What:** Shows a Windows toast (via BurntToast; falls back to a message box). With
  `-ReviewPath`/`-ApprovePath` it adds **"Review changes"** and **"Approve & apply"** buttons.
- **Trigger:** called by `wtff_pipeline_watch.js`; not normally run by hand. Manual form:
  `powershell -File wtff_notify.ps1 -Title "..." -Message "..." [-ReviewPath <f>] [-ApprovePath <f>]`

## 3. Transcription & vocabulary

### `scripts\wtff_transcribe\transcribe.js`
- **What:** Transcribes an audio file with AssemblyAI, using the campaign keyterm boost list
  + custom spelling corrections + speaker diarization. Writes a speaker-labeled transcript.
- **Trigger:** `node transcribe.js <audio_file|url> [output_path]`
  (e.g. `node transcribe.js session02.mp3`). Also called automatically by the watcher.
- **Run from:** `~\Workflows\scripts\wtff_transcribe`  ·  **Needs:** `ASSEMBLYAI_API_KEY` in the environment.

### `wtff_keyterms_sync.js`
- **What:** Scans the vault's proper-noun folders (NPCs, Locations, Flora & Fauna) and
  **appends** any new page names + aliases to `keyterms_extra.json` (add-only; never edits
  your curated base list). The transcriber merges this into its word boost.
- **Trigger:** `node wtff_keyterms_sync.js`. Also called automatically by the watcher before
  each transcription.
- **Run from:** `~\Workflows\scripts\wtff_transcribe` (the script + `keyterms_extra.json` sit
  next to `transcribe.js`, which loads the JSON via `__dirname`).

## 4. DDB party character sheets → vault

### `scripts\ddb_party_sync.js`
- **What:** Pulls full character sheets for the party from D&D Beyond and writes raw JSON +
  a readable markdown sheet into `~\03-Characters\PCs\Party Character Sheets\`. Anonymous by
  default (Public sheets only); if `DDB_COBALT` is set in `~\.env` it authenticates as you and
  also fetches Campaign-Only sheets. Reads its character roster from `scripts\ddb_party.json`.
- **Trigger:** `node ddb_party_sync.js`. Also called automatically by the watcher on each new session.
- **Run from:** `~\Workflows\scripts`  ·  **Details:** see `scripts\DDB_PARTY_SYNC.md`.

## 5. DDB dice rolls → Supabase

Three ways to get rolls into Supabase (the extension is the day-to-day one).

### `ddb-roll-sync\` — Chrome extension ("DDB Roll Sync")
- **What:** Captures your DDB Bearer token automatically (sniffs the `Authorization` header on
  game-log requests), then syncs new rolls for all active campaigns to Supabase, auto-enriching
  each roll (skill/ability/spell/weapon classification, nat20/nat1, dice parsing).
- **Triggerable actions:**
  - **"⚡ Sync All Campaigns"** button (popup) → fetches + upserts new rolls for every active campaign.
  - **"Clear"** button (popup) → clears the popup log.
  - **Auto:** token capture happens in the background whenever you browse DDB; the popup
    force-refreshes a stale token by poking an open DDB tab.
- **Trigger:** click the extension icon in Chrome, then the button. (Load it via
  `chrome://extensions` → Developer mode → Load unpacked → this folder.)

### `scripts\ddb_sync_supabase.js` — browser-console version
- **What:** Same roll sync, run manually from the DevTools console (no extension).
- **Triggerable functions (paste the script, then call):**
  - `await syncAllCampaigns('BEARER_TOKEN')` — sync every campaign.
  - `await syncCampaign('Where the Flowers Forget', 'BEARER_TOKEN')` — one campaign.
  - `await importFromExcel('path.xlsx')` — one-time bulk import (Node, needs `xlsx`).
- **Trigger:** DDB page → F12 → Console → paste → call. Get the Bearer from a Network request's
  `Authorization` header.

### `supabase-local\import_rolls_to_supabase.js` — one-time Excel import
- **What:** Migrates all rolls from `ddb_roll_archive.xlsx` into the Supabase `ddb_rolls` table
  (upsert, safe to re-run). Reads Supabase creds from `~\.env`.
- **Trigger:** `node import_rolls_to_supabase.js <path_to_xlsx>`
- **Run from:** `~\Workflows\supabase-local`  ·  **Needs:** `npm install xlsx dotenv`.

### `scripts\backfill_annotations.js` — annotation backfill
- **What:** Backfills annotation columns (action_category, ability, skill, spell, weapon,
  nat20/nat1, etc.) onto existing Supabase rolls from the "Master Rolls (Clean)" Excel sheet.
- **Trigger:** `node backfill_annotations.js <path_to_xlsx>`
- **Run from:** `~\Workflows\scripts`  ·  **Needs:** `npm install xlsx`.

## 7. OS-level trigger

### Scheduled task "WTFF Pipeline Watcher"
- **What:** Runs `start-watcher-hidden.vbs` at logon so the watcher is always up (hidden),
  surviving restarts.
- **State:** `Running` — repaired and verified 2026-08-28 by reading back the task *and* the
  processes: task `Running`, plus a `wscript.exe` wrapper and a `node.exe` running
  `wtff_pipeline_watch.js`. A watcher is only healthy when **both** processes exist.
- 🛑 **Required settings. Do NOT let these fall back to the Windows defaults.**
  This is a long-running logon watcher, and the defaults `schtasks /Create` applies will
  kill it:

  | Setting | Must be | Windows default | What the default does to you |
  |---|---|---|---|
  | `ExecutionTimeLimit` | `PT0S` (no limit) | `PT72H` | Kills the watcher every 3 days |
  | `RestartCount` | `3`, interval `PT1M` | `0` | Never comes back after a kill |
  | `StopIfGoingOnBatteries` | `False` | `True` | Dies the moment you unplug |
  | `DisallowStartIfOnBatteries` | `False` | `True` | Won't start at all on battery |

  `Install-WTFFTask.cmd` now applies all four automatically and prints them back for
  checking. 🛑 **This is the task that proved why the section is needed.** On 2026-08-28 it
  was found dead: killed at its 72h limit (last result `0x800705B4` = timeout), with
  `RestartCount=0` so it never recovered, and its `node` child left **orphaned and still
  running** under a dead `wscript` parent. Task Scheduler read `Ready`, which looks idle
  rather than broken, while a stray unmanaged watcher still held the folder. Repair was:
  fix the four settings, kill the orphan, then start the task.
- **Verify:** `Get-ScheduledTask -TaskName 'WTFF Pipeline Watcher' | Select-Object -ExpandProperty Settings`
- **Manage:** Task Scheduler → "WTFF Pipeline Watcher" (Run / End / Disable). To restart the
  watcher by hand instead, stop the `node.exe` running `wtff_pipeline_watch.js` and re-launch
  `start-watcher-hidden.vbs`. 🛑 Always stop the old `node.exe` first — starting the task
  while an orphan is alive gives you two watchers on the same folder.

## 8. Local Supabase stack (`supabase-local\`)

A standard Supabase CLI project (`supabase/config.toml`). Triggerable via the `supabase` CLI
**from the `~\Workflows\supabase-local` folder**:
- `supabase start` — boot the local stack (API on :54321, DB on :54322).
- `supabase stop` — shut it down.
- `supabase status` — show running services.
- `supabase db reset` — rebuild the local DB from migrations.

(These act on the **local** stack; the roll/party scripts above all target the **hosted**
Supabase project.)
