For a logon watcher meant to run forever that is fatal: the 72h limit killed the `wscript` wrapper every three days and `RestartCount=0` meant nothing brought it back. **The `node` child survived orphaned under a dead parent** (PID 15272, parent 15236 gone) and kept watching the folder, so Task Scheduler reported **`Ready`** — which reads as idle rather than broken — while an unmanaged stray held the files. That is why this went unnoticed.
- **Verification:** ✓ Repaired settings read back off the live task: `PT0S`, `RestartCount=3`, both battery flags `False`. ✓ Orphan killed **before** restarting, so there is exactly one watcher, not two. ✓ Task now `Running` with **both** processes alive (`wscript.exe` 15500 + `node.exe` 35132). ✓ Installer's embedded PowerShell syntax-checked with the PS parser (0 errors). ✓ Compared against the healthy `SITL Pipeline Watcher`, which had the correct values all along from an undocumented hand-fix — that asymmetry is what made this diagnosable.
- **Watch out:** 🛑 **A watcher is only healthy when BOTH a `wscript.exe` and a `node.exe` exist for it.** Task state alone lies: this one read `Ready` while broken. Check processes, not just Task Scheduler. ⚠️ **Scope — this fixes the task lifecycle ONLY.** The **misrouting** bug in Next Steps (this watcher wrote SITL audio into this vault twice on 2026-08-02) is a *different* defect in `wtff_pipeline_watch.js` and is **completely untouched**.
